# TaskPulse free-tier audit

**Audited:** 2026-11-11
**Release gate:** production must remain on Cloudflare Workers Free and Firebase Spark. No billing account may be attached, and no quota failure may trigger an upgrade.

This audit covers the infrastructure and third-party services planned for the Android app and backend. Usage figures are engineering estimates for an early deployment, not provider guarantees. Recheck the linked primary documentation before each release because provider limits can change.

## Consumption model and guardrails

- Production capacity depends strongly on how long users keep dashboard/task screens in the foreground. The 25-second refresh runs only in foreground; a rough high-use estimate is `members × foreground-hours × 3600/25 × requests-per-refresh`. For example, 30 members × 4 hours × 2 calls per refresh is about 34,560 HTTP requests/day, plus 1,440 Cron calls and other app actions. This is below 100,000, but leaves limited room for bursty use and other Workers on the account. A higher-usage team must shorten foreground time/use fewer refreshes or accept temporary service errors; never upgrade.
- Cron work is split across indexed scans for reminders, overdue events, and outbox deliveries. Each query is capped; a run never reads an entire task, membership, or device-token table. To stay well below the 10 ms Free CPU ceiling, the current scheduler handles at most one overdue candidate and one reminder candidate per minute, one fan-out page of 10 recipients, and three notification recipients (up to two devices each). This is a hard throughput limit: a sustained arrival rate above one new overdue task per minute can build a detection backlog, and large teams may take multiple minutes to receive a fan-out. Check the heartbeat and D1 backlog, and do not rely on exact-minute delivery until measured on the actual account.
- API calls write one indexed rate-limit counter per authenticated request. Profile synchronization avoids a D1 write when the Firebase profile has not changed. Include those writes plus task/activity/notification work in the daily D1 write budget; polling can be well below the D1 100,000 row-write cap at the example 30-member scenario, but leaves less headroom than the HTTP request count alone suggests.
- The scheduler stores a heartbeat and bounded work cursors in D1. D1 usage and Worker request/CPU usage must be checked in the Cloudflare dashboard. Firebase Auth and FCM quota/health must be checked in their dashboards.
- On exhausted quotas or provider errors, the app shows a retryable error, stops retry storms, preserves pending outbox work, and resumes after the provider's reset/recovery. There is no code path that changes a billing plan.
- Firebase Spark's documented behavior for many no-cost products is to stop that product's service after a quota is reached until reset; do not respond by linking billing. D1 Free returns errors until its daily reset. Worker Free rejects invocations over its request/CPU limits.
- A physical FCM test requires project-owner Firebase configuration and at least one real Android device with working Google Play services. A test receipt never establishes guaranteed delivery for force-stopped apps.

## Local environment audit

At audit time, system Node.js 24.18.0, npm 11.16.0 and JDK 17 were present. Firebase CLI 15.29.0 is installed. The pinned `cf` npm package requires Node 24.22 or later; a checksum-verified Node 24.22.2 portable distribution was used from the temporary directory to run `cf build`, local D1 migration, and `cf dev`, without changing the system Node installation. Flutter, Dart, ADB, and Android SDK platform/build-tools are absent. `ANDROID_HOME` points to `D:\Android\SDK`, but that SDK directory is absent. No Firebase app configuration, Cloudflare account session, or service-account credentials are present. APK build and live deployment therefore remain blocked until the owner configures the free accounts and local Android toolchain; no credentials are stored in this repository.

## Go/no-go findings

1. The named production services have permanent no-cost options; the app can be designed to stop gracefully on quota exhaustion.
2. The 10 ms Cloudflare Free CPU cap per Cron invocation is the main architecture risk for one-minute deadline processing combined with cryptographic FCM token signing. Implementation and emulator measurements are required before any claim of production feasibility.
3. No backend can be deployed or push notifications can be physically verified until the owner completes account-specific Cloudflare/Firebase setup. A blocked setup must not be worked around by enabling billing.
