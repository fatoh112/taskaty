**Audited:** 2026-11-12 (Africa/Cairo)
**Release gate:** production must remain on Cloudflare Workers Free and Firebase Spark. No billing account may be attached, and no quota failure may trigger an upgrade.

This audit covers the infrastructure and third-party services planned for the Android app and backend. Usage figures are engineering estimates for an early deployment, not provider guarantees. Recheck the linked primary documentation before each release because provider limits can change.

## Consumption model and guardrails

- Production capacity depends strongly on how long users keep dashboard/task screens in the foreground. The 25-second refresh runs only in foreground; a rough high-use estimate is `members × foreground-hours × 3600/25 × requests-per-refresh`. For example, 30 members × 4 hours × 2 calls per refresh is about 34,560 HTTP requests/day, plus 1,440 Cron calls and other app actions. This is below 100,000, but leaves limited room for bursty use and other Workers on the account. A higher-usage team must shorten foreground time/use fewer refreshes or accept temporary service errors; never upgrade.
- Cron work is split across indexed reminder/overdue scans, bounded team fan-out, and a persistent FCM outbox. Each run examines at most five overdue tasks and five reminders, claims at most three fan-out events (up to 30 members per event), and claims at most 15 notification recipients (up to two device tokens each). The configured worst-case budget is about 14 D1 calls plus 31 Google/FCM fetches = 45 subrequests, below the 50 subrequest ceiling. Idle ticks group the start heartbeat with both indexed deadline scans and group an empty outbox claim with the completion heartbeat. Version #7 also batches fanout member-page reads and writes, and commits no-device/missing-notification states with the outbox delivery query. Local tests cover duplicate suppression, races, fanout, retries, and no-device handling. Live v7 CPU passed 20 idle ticks (max 8.440 ms) and controlled overdue/fanout (7.253 ms) and reminder (5.482 ms) samples. The actual device-backed FCM send path is not represented by those no-device Cron tests.
- Load test evidence: ten overdue tasks for a 30-member team with two devices per member produced 300 persistent notification rows and drained 300 mocked deliveries in 21 simulated minute ticks; detection latency p50 1 minute, p95 2, max 2; one transient FCM failure retried; peak observed combined subrequests 46. A 100-task backlog after a ten-minute scheduler outage produced all 100 logical events and 3,000 persistent notifications; maximum due-to-detection delay was 29 minutes, and 3,000 mocked recipient records drained in 201 ticks with one retry. These are deterministic local tests, not Cloudflare production measurements.
- API calls write one indexed rate-limit counter per authenticated request. Profile synchronization avoids a D1 write when the Firebase profile has not changed. Include those writes plus task/activity/notification work in the daily D1 write budget; polling can be well below the D1 100,000 row-write cap at the example 30-member scenario, but leaves less headroom than the HTTP request count alone suggests.
- The scheduler stores a heartbeat and bounded work cursors in D1. Cloudflare D1 Insights for UTC 2026-11-11 00:00–23:10 reported 4,476 rows read, 1,151 written and 1,956 queries; current database size is 266,240 bytes. Against the documented daily caps, that is 0.090% of the read quota and 1.151% of the write quota at the time queried; this includes controlled fixture writes and cleanup. Cloudflare's `events.workersInvocations` schema reports Cron invocation type directly and defines `cpuTimeUs` in microseconds; startup CPU is separate and excluded. Production CPU profiling returned `The Worker has no loaded isolate in its recent execution locations`, so function-level attribution remains unavailable. Firebase Auth and FCM quota/health still require monitoring in their dashboards.
- On exhausted quotas or provider errors, the app shows a retryable error, stops retry storms, preserves pending outbox work, and resumes after the provider's reset/recovery. There is no code path that changes a billing plan.
- Firebase Spark's documented behavior for many no-cost products is to stop that product's service after a quota is reached until reset; do not respond by linking billing. D1 Free returns errors until its daily reset. Worker Free rejects invocations over its request/CPU limits.
- A physical FCM test requires project-owner Firebase configuration and at least one real Android device with working Google Play services. A test receipt never establishes guaranteed delivery for force-stopped apps.

## Go/no-go findings

1. The named production services have permanent no-cost options; the app can be designed to stop gracefully on quota exhaustion.
2. Baseline live Cloudflare telemetry showed 21/189 Cron samples above Free's 10 ms CPU budget. Version #7's 20 idle Cron samples and controlled overdue/fanout and reminder ticks all stayed below 10 ms. The device-backed FCM send path still needs a valid token/device to measure its CPU and delivery behavior.
3. FCM credentials are configured securely and the server reached FCM HTTP v1, but physical notification delivery remains unverified because no valid device token/device was available. A blocker must not be worked around by enabling billing.
